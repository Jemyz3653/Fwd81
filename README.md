# Fwd81

Слой совместимости, позволяющий запускать приложения, собранные под **Windows 10 x64**,
на **Windows 8.1 x64**. Название — от «forward to 8.1».

Направление ровно одно: программа для Win10 → компьютер с Win8.1. Обратное не поддерживается.

## Состояние: веха M2 — ядро и внедрение

Ядро `fwd81core.dll` (без библиотеки языка C, только `ntdll`) при загрузке в процесс
**записывает факт загрузки** в журнал. Команды `fwd81cli enable/disable/uninstall`
включают и выключают Fwd81 для программы через реестр IFEO (плюс кладут/убирают
`fwd81core.dll` в System32). `fwd81cli log` показывает журнал.

**Что проверено, а что нет** (честно, потому что это важно):
- журналирование при загрузке — **проверено вживую**: ядро грузили в процесс, оно
  записало событие с временем, PID и путём к образу;
- само внедрение через IFEO (чтобы ядро попадало в чужую программу автоматически) —
  **код готов, но вживую ещё не проверено**: для этого нужна запись в System32 и HKLM
  (права администратора), и делать это лучше на виртуальной машине с 8.1. До проверки
  считать «внедрение работает» нельзя. Пока безопасно посмотреть план — `--dry-run`.

| Веха | Что в ней | Готово |
|---|---|:---:|
| M0 | каркас репозитория, сборка, CI, документация | ✅ |
| M1 | exportdiff + `fwd81diag.exe` — анализ, «запустится ли программа» | ✅ |
| M2 | ядро без CRT + журнал загрузки + команды IFEO | журнал ✅, внедрение не проверено |
| M3 | перехваты загрузчика, подстановка отсутствующих функций | — |
| M4 | `fwd81_kernel32`, `fwd81_ntdll` — первые реализации функций | — |
| M5 | слой DPI из Windows 10 | — |
| M6 | спуф версии, профили, `fwd81cli patch`, режим без прав администратора | — |
| M7 | окно настроек, заглушки apiset, установщик | — |
| M8 | обёртки dxgi, таблица совместимости, релиз 0.1 | — |

## Какие ошибки это должно лечить

- «Точка входа в процедуру X не найдена в библиотеке DLL Y»
- «Не найден `api-ms-win-core-...dll`»
- «Это приложение невозможно запустить на вашем ПК»
- искусственные проверки версии системы внутри программы

## Чего проект не делает

Это не список «пока не сделали», это список **принципиально невозможного или
сознательно исключённого**:

- **Direct3D 12** — требует частей в ядре системы и в драйверах видеокарты, из
  пользовательского режима не воспроизводится.
- **Приложения UWP из Магазина и WinRT-интерфейсы Windows 10** (`Windows.UI.*`,
  CoreMessaging) — это отдельная подсистема, а не набор функций.
- **Всё, что требует своего драйвера или изменений ядра.**
- **x86 (32-разрядные программы) и ARM64** — возможно позже, сейчас только x64.
- **Windows 7 и старше** — для них есть [VxKex](https://github.com/vxiiduu/VxKex).
- **Игры с защитой и античитами** (Denuvo, VMProtect, EasyAntiCheat) — механизм
  внедрения через Application Verifier они часто принимают за отладчик и блокируют
  запуск. Для таких случаев предусмотрен режим без записи в реестр (веха M6), но
  гарантий нет.

### Один файл в System32 — и почему это не то, чего вы боитесь

**Fwd81 никогда не изменяет, не подменяет и не удаляет файлы Microsoft** в
`C:\Windows\System32` и `SysWOW64`. Именно подмена системных файлов убивает систему
насмерть — и мы этого не делаем.

Но основной способ работы Fwd81 требует положить в `System32` **один свой файл** —
`fwd81core.dll`. Это не наша прихоть: механизм Windows под названием Application
Verifier, через который Fwd81 попадает в программу, принимает только имя файла и ищет
его строго в `System32`, полные пути не поддерживает (так сделано намеренно, ради
безопасности). Точно так же устроен VxKex.

Файл наш, с уникальным именем `fwd81*` — перепутать его с системным нельзя. Команда
`fwd81cli uninstall` убирает его из `System32` начисто и вычищает все следы в реестре.
Всё остальное — библиотеки реализаций, заглушки, профили — лежит в каталоге установки
Fwd81 и `System32` не касается.

Если даже один свой файл в `System32` для вас неприемлем или у вас нет прав
администратора — есть режим без записи в систему (правка копии программы), он слабее;
подробности в [docs/limitations.md](docs/limitations.md).

## Сборка

Нужны: Windows x64, Visual Studio 2022 с рабочей нагрузкой «Разработка классических
приложений на C++», CMake 3.25+, Ninja, Python 3 с модулем `pefile` (для проверок).

```
git clone https://github.com/Jemyz3653/Fwd81.git
cd Fwd81
.\build.ps1
```

Скрипт сам находит компилятор и поднимает его окружение — отдельная «командная строка
разработчика» не нужна. Результат ляжет в `build\bin\Debug\` и `build\bin\Release\`.

Полезные ключи:

```
.\build.ps1 -Config Release   только Release
.\build.ps1 -Clean            снести каталог build и собрать заново
.\build.ps1 -NoChecks         без проверок, быстрее
```

Из `cmd.exe` то же самое: `build.bat`.

## Что получается на выходе

| Файл | Что это |
|---|---|
| `fwd81core.dll` | ядро: попадает в процесс раньше, чем программа начнёт искать функции; пока пишет в журнал факт загрузки (перехваты — M3) |
| `fwd81cli.exe` | командная утилита (`version`, `help`, `diag`, `enable`, `disable`, `uninstall`, `log`) |
| `fwd81diag.exe` | анализатор: «запустится ли эта программа на 8.1» — **работает** |
| `fwd81cfg.exe` | окно настроек (веха M7) |
| `fwd81_*.dll` | библиотеки реализаций функций Windows 10 (веха M4+) |

## Проверки, которые выполняются при каждой сборке

Три правила проекта проверяются механически, а не обещаниями:

1. `fwd81core.dll` **не зависит ни от чего, кроме `ntdll.dll`** — ядро попадает в чужой
   процесс раньше, чем там заведётся библиотека языка C.
2. Все наши исполняемые файлы **запускаются на самой Windows 8.1** — в заголовке файла
   не должно быть требования версии выше 6.3.
3. **Лицензионная граница не нарушена** — см. ниже.

Скрипты: `tools/check_image.py`, `tools/check_licenses.py`. Каждый проверен тем, что
ему подсовывали заведомо испорченный файл и убеждались, что он падает и называет виновника.

## На что опирается замысел

- [VxKex](https://github.com/vxiiduu/VxKex) — тот же подход для Windows 7. Основная
  архитектурная модель: внедрение через реестр, перехват загрузчика, профили на каждую
  программу, системные файлы не трогаются.
- [One-Core-API](https://github.com/Skulltrail192/One-Core-API-Binaries) — оттуда взята
  идея поставлять готовые DLL с именами новых системных библиотек. Подход с заменой
  системных файлов — не взят сознательно.

Код Microsoft не копируется. Из обоих проектов выше взяты только архитектурные идеи.
