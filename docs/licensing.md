# Лицензии проекта Fwd81

В проекте **две лицензии**, и граница между ними проходит **строго по каталогам**.
Это не формальность: от неё зависит, какой чужой код мы имеем право взять.

## Граница

| Каталог | Лицензия | Что там лежит |
|---|---|---|
| `src/core/` | **LGPL-2.1-or-later** | `fwd81core.dll` — ядро внедрения |
| `src/libs/` | **LGPL-2.1-or-later** | `fwd81_*.dll` — реализации функций Windows 10 |
| `src/apisets/` | **LGPL-2.1-or-later** | генерируемые заглушки apiset-контрактов |
| `src/cli/` | **MIT** | `fwd81cli.exe` |
| `src/diag/` | **MIT** | `fwd81diag.exe` |
| `src/cfg/` | **MIT** | `fwd81cfg.exe` |
| `tools/` | **MIT** | exportdiff и проверочные скрипты |
| `tests/` | **MIT** | тесты (появятся в вехе M3) |
| `.github/` | **MIT** | настройки CI |
| `CMakeLists.txt`, `build.ps1`, `build.bat` в корне | **MIT** | файлы сборки |

Тексты лицензий: `LICENSE` (LGPL-2.1) и `LICENSE.MIT` (MIT).

**Перенос кода между зонами запрещён без отдельного решения владельца проекта.**
Скопировать функцию из `src/libs/` в `src/cli/` — значит нарушить лицензию,
даже если это «всего пара строк» и «мы же сами это писали»: часть кода в
LGPL-зоне может оказаться заимствованной из Wine.

## Почему именно так

**Ядру и библиотекам нужна LGPL**, потому что это единственный способ законно
переиспользовать код Wine. Реализации сотен функций `Rtl*`, поведение
недокументированных структур ntdll, разбор apiset-схемы — всё это в Wine уже
написано и проверено годами. Писать это заново «по документации» медленнее
и, что важнее, рискованнее: документации на недокументированное не существует.

**Утилитам LGPL не нужна.** Анализатор, командная утилита, окно настроек и
скрипты не содержат и не будут содержать заимствований — это наш собственный
код от первой строки. Под MIT их может свободно взять кто угодно, в том числе
в закрытый продукт, и это ничему не мешает.

Обязательство LGPL, которое мы на себя берём: тот, кто соберёт Fwd81 в свой
продукт, обязан отдавать изменения **нашего** кода. Его собственный код при
этом остаётся закрытым — этим LGPL и отличается от GPL.

## Что можно копировать, а что нельзя

### Wine — можно

Лицензия Wine — LGPL-2.1-or-later, ровно наша. Код можно брать **только в зоны
LGPL** (`src/core/`, `src/libs/`, `src/apisets/`).

Обязательно при этом:
- сохранить авторские строки из исходного файла;
- в шапке нашего файла указать: из какого файла Wine, из какого коммита взято;
- **добавить запись в `NOTICE` в том же коммите.**

### ReactOS — почти нельзя

ReactOS целиком лицензирован под **GPL-2.0-or-later**, а не под LGPL. Взять
оттуда произвольный файл — значит утянуть весь Fwd81 в GPL, то есть обязать
всех, кто нас использует, открывать свой код. Этого мы не хотим.

Исключение ровно одно: файлы ReactOS, **в шапке которых явно написано LGPL**
и указано происхождение из Wine (ReactOS переиспользует часть кода Wine).
Такой файл — это по сути файл Wine, и брать его можно на условиях выше.

Проверять надо **шапку конкретного файла**, а не лицензию проекта в целом.

### VxKex и One-Core-API — только идеи

Из них взята архитектура: внедрение через реестр, перехват загрузчика, профили
на каждую программу, поставка DLL с именами новых системных библиотек.
**Код не копируем**, пока не проверим их лицензии отдельно и не запишем решение
сюда.

### Код Microsoft — никогда

Ни из дизассемблера, ни из утёкших исходников, ни из примеров с ограничивающей
лицензией. Заголовки Windows SDK использовать можно и нужно — они для того
и поставляются; речь о коде реализации.

Допустимый источник сведений о функции: документация Microsoft на learn.microsoft.com,
заголовки SDK, публичные символы отладки, собственные наблюдения за поведением.
В комментарии к каждой реализуемой функции указывается, откуда взята сигнатура
и в какой версии Windows функция появилась.

## Как это проверяется

Руками такие правила не держатся — забываются на третьей неделе. Поэтому есть
`tools/check_licenses.py`. Он требует, чтобы:

1. в каждом исходном файле стояла строка `SPDX-License-Identifier` с лицензией
   его каталога;
2. в файле **не упоминалась чужая лицензия** — так ловится копипаста между зонами;
3. каждый исходный файл попадал в какую-то описанную зону: файл в новом каталоге,
   не внесённом в правила, считается нарушением, а не «пока не решили».

Проверка запускается при каждой сборке (`build.ps1`) и в CI.

Единственное исключение из пункта 2 — сам `tools/check_licenses.py`: ему приходится
называть обе лицензии, он же их сравнивает. Исключение прописано в нём поимённо.

Работоспособность проверялась не рассуждением, а поломкой: в каталог `src/core/`
подкладывался файл с пометкой MIT, файл без пометки вовсе и файл в неописанном
каталоге. Все три случая скрипт отверг и назвал виновника по имени (15.09.2026).
