# Как проверять Fwd81

Документ живой: с каждой вехой сюда добавляется её сценарий проверки. Разделы,
помеченные «(нужна виртуальная машина)», выполняются на живой Windows 8.1 — в CI
их нет и быть не может, потому что раннеры GitHub это Windows Server.

Напоминание, ради которого всё это написано: **прогон по API доказывает, что
механизм работает, и молчит о том, есть ли у человека кнопка.** Пункт считается
готовым только после того, как действие проверено руками и глазами.

---

## Что делает CI

При каждом изменении в ветке `main` и в каждом запросе на слияние:

1. сборка x64 в конфигурациях Debug и Release;
2. проверка лицензионной границы (`tools/check_licenses.py`);
3. проверка, что `fwd81core.dll` зависит только от `ntdll.dll`;
4. проверка, что в заголовках наших файлов не записано требование Windows выше 6.3;
5. запуск `fwd81cli version` — файл действительно стартует;
6. собранное складывается в артефакт `fwd81-x64` и хранится 14 дней.

Чего CI **не** проверяет: работу на Windows 8.1, работу самого механизма внедрения,
поведение с реальными программами. Всё это — ручные сценарии ниже.

---

## Веха M0 — каркас. Проверка на этой машине

Время: около трёх минут.

### 1. Сборка с нуля

```powershell
cd C:\Fwd81
.\build.ps1 -Clean
```

Должно закончиться зелёной строкой `Готово.` Внутри по дороге пройдут проверки —
все должны написать `Проверка пройдена.` и `Лицензионная граница в порядке`.

### 2. Файлы на месте

```powershell
dir C:\Fwd81\build\bin\Release
```

Ожидается: `fwd81core.dll` и `fwd81cli.exe` (плюс отладочные `.pdb`).

### 3. Утилита работает и честно говорит о незаконченном

```powershell
C:\Fwd81\build\bin\Release\fwd81cli.exe version
C:\Fwd81\build\bin\Release\fwd81cli.exe help
C:\Fwd81\build\bin\Release\fwd81cli.exe diag test.exe
```

Ожидается: версия и справка на русском без «кракозябр»; команда `diag` отвечает,
что появится в вехе M1, и возвращает код 2. Проверить код возврата:

```powershell
C:\Fwd81\build\bin\Release\fwd81cli.exe diag test.exe; $LASTEXITCODE
```

Должно показать `2`.

### 4. Сторожа действительно сторожат

Смысл проверки: убедиться, что скрипт не просто пишет «всё хорошо», а умеет падать.

```powershell
cd C:\Fwd81
py -3 tools\check_image.py build\bin\Release\fwd81cli.exe --imports ntdll.dll
```

Ожидается: **НАРУШЕНИЕ** с упоминанием `KERNEL32.dll` и код возврата 1. Это
правильное поведение: утилите зависеть от kernel32 положено, мы нарочно натравили
на неё правило, написанное для ядра.

```powershell
py -3 tools\check_image.py C:\Windows\System32\notepad.exe
```

Ожидается: **НАРУШЕНИЕ** «требование Windows 10.0». Это наглядно показывает саму
задачу проекта: системный блокнот от Windows 11 на 8.1 не запустился бы вовсе.

## Веха M0 — проверка на живой Windows 8.1 *(нужна виртуальная машина)*

Выполнить сразу, как только виртуальная машина будет установлена. Это закрывает
**открытый вопрос №2** из [architecture.md](architecture.md).

1. Скопировать на виртуальную машину `build\bin\Release\fwd81cli.exe` — **один файл,
   больше ничего**.
2. Запустить в командной строке: `fwd81cli.exe version`.

**Ожидается:** версия выводится, русский текст читается. Это доказывает, что
статическая библиотека языка C из Visual Studio 2022 работает на 8.1 и наши утилиты
не требуют от пользователя ни `vcruntime140.dll`, ни обновления UCRT KB2999226.

**Если не запустится:** записать точный текст ошибки в [ЖУРНАЛ.md](ЖУРНАЛ.md).
Вероятные причины по убыванию: нужен пакет обновлений для 8.1; набор инструментов
Visual Studio 2022 требует чего-то отсутствующего в 8.1; метка версии в заголовке
файла всё-таки не та. Лечение будет разным, гадать заранее незачем.

---

## Что понадобится от виртуальной машины дальше

Чтобы не устанавливать её дважды, сразу после установки Windows 8.1 нужно:

1. **Скопировать `C:\Windows\System32` целиком** (или хотя бы все `*.dll`) в
   `C:\Fwd81\data\system32-win81\` на основной машине. Без этого не работает
   `exportdiff`, а без него — вся веха M1.
2. Зафиксировать в [ЖУРНАЛ.md](ЖУРНАЛ.md): точная версия сборки 8.1, стоят ли
   обновления, стоит ли KB2999226 (UCRT).
3. Сделать снимок состояния (snapshot) чистой системы — к нему придётся возвращаться
   после каждого неудачного опыта с реестром.

## Веха M1 — анализатор. Проверка на этой машине

Время: около двух минут (плюс минута на обход System32).

### 1. Инструменты собрались

После `.\build.ps1` в `build\bin\Release` должен появиться `fwd81diag.exe`.

### 2. exportdiff читает System32 и честно молчит про 8.1

```powershell
cd C:\Fwd81
py -3 tools\exportdiff\exportdiff.py all
```

Ожидается: обход `C:\Windows\System32` (~минуту, ~140 тыс. функций), затем сообщение,
что данных Windows 8.1 пока нет, и это ожидаемо. `data\missing.json` должен содержать
`"available": false` — а НЕ пустой список (пустой означал бы «ничего не отсутствует»).

### 3. fwd81diag показывает требуемую версию Windows

```powershell
.\build\bin\Release\fwd81diag.exe C:\Windows\System32\notepad.exe
```

Ожидается: `Требуемая версия Windows (из заголовка): 10.0` с предупреждением, что 8.1
такой файл не примет без `patch`; список импортируемых библиотек; вердикт «невозможен
без базы 8.1» и код возврата 5 (`$LASTEXITCODE`). На нашем же `fwd81cli.exe` версия
будет 6.3 — «файл 8.1 примет».

### 4. То же через общую утилиту (проверка делегирования)

```powershell
.\build\bin\Release\fwd81cli.exe diag C:\Windows\System32\notepad.exe
```

Должно дать тот же вывод: `fwd81cli diag` не дублирует разбор, а зовёт `fwd81diag.exe`.

### Что проверено разработчиком (а не только описано)

Логика вердикта проверена не рассуждением, а на живом входе. На `fwd81cli.exe`
подставлялась синтетическая база 8.1, из которой убиралась функция `GetStdHandle`:

- функция не покрыта → вердикт **НЕ ЗАПУСТИТСЯ**, код 4;
- покрыта заглушкой (S) → **С ОГРАНИЧЕНИЯМИ**, код 3;
- покрыта полноценно (F) → **ЗАПУСТИТСЯ**, код 0.

Разбор PE проверен на настоящих файлах Windows 11 (notepad и наши утилиты).

## Веха M1 — проверка на живой Windows 8.1 *(нужна виртуальная машина)*

После того как появится копия System32 из 8.1 и база будет перегенерирована:

1. Взять программу с известным поведением и прогнать `fwd81diag` на основной машине —
   получить вердикт.
2. Ту же программу попробовать запустить на живой 8.1 (без Fwd81).
3. **Сверить:** вердикт «не запустится» должен совпасть с реальным отказом, а «запустится»
   — с реальным запуском. Расхождения записать в этот файл: они и есть карта того, что
   анализатор ещё не учитывает (форвардеры, ординалы, косвенные зависимости).

Это и есть смысл правила «круговой тест не доказывает формат»: сверяемся с настоящим
загрузчиком 8.1, а не сами с собой.

## Веха M2 — ядро и журнал. Проверка на этой машine

### 1. Ядро пишет журнал при загрузке (безопасно, без прав администратора)

Загружаем ядро в процесс через `LoadLibrary` — это НЕ трогает System32 и реестр:

```powershell
$log = "$env:LOCALAPPDATA\Fwd81\logs\fwd81.log"
if (Test-Path $log) { Remove-Item $log -Force }
$sig = '[DllImport("kernel32", CharSet=CharSet.Unicode)] public static extern System.IntPtr LoadLibraryW(string p); [DllImport("kernel32")] public static extern bool FreeLibrary(System.IntPtr h);'
$k = Add-Type -MemberDefinition $sig -Name L -Namespace W -PassThru
$h = $k::LoadLibraryW("C:\Fwd81\build\bin\Release\fwd81core.dll")
[void]$k::FreeLibrary($h)
C:\Fwd81\build\bin\Release\fwd81cli.exe log
```

Ожидается: в журнале две строки — «загружено в процесс» и «выгружено из процесса»,
с временем, `pid=` и `image=...powershell.exe`. Кириллица читается.

### 2. План внедрения без записи (безопасно)

```powershell
C:\Fwd81\build\bin\Release\fwd81cli.exe enable --dry-run notepad.exe
C:\Fwd81\build\bin\Release\fwd81cli.exe uninstall --dry-run
```

Ожидается: показан план (копирование в System32, ключ IFEO), затем «это dry-run:
ничего не записано». Система не меняется.

## Веха M2 — проверка внедрения через IFEO *(меняет систему, нужно разрешение или ВМ)*

Это единственная часть M2, которую нельзя проверить, ничего не меняя: `enable`
пишет `fwd81core.dll` в `C:\Windows\System32` и ключи в `HKLM` (нужны права
администратора). Делать это на рабочей машине — только с явного согласия Арсения;
правильнее — на виртуальной машине с 8.1.

Порядок проверки (на подопытной, заведомо безобидной программе):

```powershell
# от имени администратора:
fwd81cli enable app.exe          # включить
app.exe                          # запустить программу
fwd81cli log                     # ожидается строка «загружено в процесс ... image=...app.exe»
fwd81cli disable app.exe         # выключить
fwd81cli uninstall               # убрать наш файл из System32 и все ключи IFEO
```

**Успех** = после `enable` в журнале появляется факт загрузки ядра именно в целевую
программу (а не только в наш тестовый LoadLibrary). Это доказывает, что механизм
`VerifierDlls` действительно подхватывает наш файл из System32 — открытый вопрос №1
из [architecture.md](architecture.md) закрывается только этим опытом.

**Откат** обязателен после проверки: `uninstall` должен убрать всё начисто (проверить,
что `fwd81core.dll` в System32 исчез и наших ключей IFEO не осталось).
