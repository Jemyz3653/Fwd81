## 15.09.2026 — веха M0: каркас

### Что сделано

- Заведён репозиторий в `C:\Fwd81` поверх существующей истории GitHub (первый
  коммит от 14.09.2026 сохранён, не затёрт).
- Собран каркас: система сборки на CMake + Ninja, два скрипта запуска, CI на GitHub
  Actions, документация, два сторожа-проверки.
- Собирается и работает: `fwd81core.dll` (пустой каркас ядра, без библиотеки языка C)
  и `fwd81cli.exe` (команды `version` и `help`; остальные честно отвечают, что ещё
  не реализованы).

### Принятые решения и причины

**1. Две лицензии вместо одной, граница по каталогам.**
В репозитории лежала MIT (создана вместе с репозиторием на GitHub), в задании
значилась LGPL-2.1+. Решение владельца проекта: ядро, библиотеки реализаций и
заглушки apiset — под LGPL-2.1-or-later, утилиты и инструменты — под MIT.

Причина: LGPL в зоне ядра нужна, чтобы иметь право брать код Wine. Утилиты
заимствований не содержат, им ограничения ни к чему.

Отдельно уточнено (и это важная поправка к заданию): **ReactOS лицензирован под
GPL-2.0-or-later, а не под LGPL.** Произвольный файл оттуда утянул бы весь проект
в GPL. Легальный источник заимствований остаётся один — Wine, плюс те файлы
ReactOS, где в шапке явно указан LGPL и происхождение из Wine. Подробности —
в [licensing.md](licensing.md).

**2. Генератор сборки — Ninja Multi-Config, а не генератор Visual Studio.**
На этой машине CMake 4 с генератором Visual Studio в некоторых проектах падает на
`ucrtd.lib`. Ninja этой проблемы не имеет и собирает быстрее. Обе конфигурации
(Debug и Release) настраиваются одним заходом.

**3. `build.ps1` сам поднимает окружение компилятора.**
Отдельная «командная строка разработчика» не нужна: скрипт находит Visual Studio
через `vswhere` (обязательно с ключом `-products *`, иначе не видно Build Tools)
и импортирует окружение `vcvars64.bat`.

Попутно вылезла особенность этой машины: в ней включён
`NoDefaultCurrentDirectoryInExePath`, из-за чего `vcvars64.bat` не находит свой же
`vswhere.exe` и пишет `is not recognized`. Окружение при этом всё равно
поднималось, но шум в выводе убран — каталог установщика добавляется в PATH
перед вызовом.

**4. Утилиты собираются со статической библиотекой языка C.**
Требование задания — утилиты должны запускаться на самой Windows 8.1. Статическая
CRT снимает зависимость и от `vcruntime140.dll`, и от обновления UCRT KB2999226,
которого на машине пользователя может не быть. Результат: `fwd81cli.exe` зависит
ровно от одной библиотеки — `KERNEL32.dll`. Проверено на собранном файле.

**5. Метка подсистемы 6.03 у всех наших исполняемых файлов.**
Иначе компоновщик пишет в заголовок «нужна Windows 10.0», и 8.1 откажется
запускать файл ещё до поиска функций — то есть мы наступили бы ровно на ту
проблему, которую чиним. Задаётся флагом `/SUBSYSTEM:<вид>,6.03`.

**6. Три правила проекта отданы сторожам, а не дисциплине.**
Правило, которое проверяет человек, забывается на третьей неделе.

| Сторож | Что ловит |
|---|---|
| `tools/check_image.py` | зависимость ядра от чего-либо кроме `ntdll.dll`; требование Windows выше 6.3 в заголовке |
| `tools/check_licenses.py` | нарушение лицензионной границы между каталогами |

**7. Сторожа проверены поломкой, а не рассуждением.** Каждому подсовывали заведомо
испорченный вход, и каждый обязан был упасть **и назвать имя виновника**:

- проверка зависимостей: натравлена на `fwd81cli.exe` с правилом «только ntdll» →
  назвала `KERNEL32.dll`, код возврата 1;
- проверка версии в заголовке: натравлена на `C:\Windows\System32\notepad.exe` →
  «требование Windows 10.0», код возврата 1;
- проверка лицензий, три случая: MIT-файл в каталоге `src/core`; файл без пометки
  SPDX вовсе; файл в каталоге, не описанном в правилах. Все три отвергнуты с именем
  файла.

**8. Каталоги будущих частей не пустые, а с объяснением.**
В `src/libs`, `src/apisets`, `src/diag`, `src/cfg` лежит `README.md`: что там
появится и в какой вехе. Пустой каталог без объяснения — это вопрос «а это вообще
живое?» через два месяца.

**9. Незаконченное говорит о себе вслух.**
`fwd81cli` на команды `diag`, `enable`, `run`, `patch`, `list`, `log` отвечает
текстом «появится в вехе такой-то» и кодом возврата 2. Ни одна команда не делает
вид, что отработала. Заглушка, которая молча врёт «всё получилось», в проекте
запрещена.

### Что проверено своими руками

- Сборка с нуля в Debug и Release — проходит.
- `fwd81cli.exe version` и `help` — выводят русский текст без «кракозябр».
- `fwd81cli.exe diag test.exe` — код возврата 2, честное сообщение.
- `fwd81core.dll` — в таблице импорта **ноль** зависимостей (кода, который звал бы
  ntdll, там пока просто нет), требование в заголовке 6.0.
- `fwd81cli.exe` — одна зависимость `KERNEL32.dll`, требование в заголовке 6.3.
- Все три сторожа — падают там, где должны.

### Что НЕ проверено

- **Ничего не проверено на живой Windows 8.1.** Виртуальной машины пока нет.
- CI на GitHub Actions написан, но ни разу не запускался: изменения ещё не

## 15.09.2026 (вечер) — уточнение главного запрета: один файл в System32 разрешён

### Что произошло

M0 отправлена на GitHub, CI запустился. Сразу после этого владелец проекта закрыл
самый крупный открытый риск — **не опытом, а документацией**, и заявил, что риск
подтверждён: механизм `VerifierDlls` принимает только имя файла, ищет поставщика
строго в `%SystemRoot%\System32`, полные пути не поддерживает **намеренно, ради
безопасности**. Обойти нельзя — ограничение в самом Application Verifier.

Раньше я держал это открытым вопросом «проверить на ВМ». Проверять нечего: поведение
документировано и однозначно. Открытый вопрос №1 закрыт.

### Принятое решение (уточнение §3 задания, правило 1)

Прежняя формулировка «никогда ничего не класть в System32» была **слишком широкой** и
сделала бы основной способ внедрения невозможным. Новая редакция:

> Запрещено изменять, подменять, патчить и **удалять** любые файлы **Microsoft** в
> `System32` и `SysWOW64`. Разрешено добавлять туда **свои** файлы с уникальным именем
> `fwd81*`, и только их.

Требования к такому файлу (все обязательны):
- имя уникальное (`fwd81core.dll`) — коллизия с системным исключена;
- установщик умеет снять его начисто;
- у `fwd81cli` есть команда `uninstall` — убирает файл из `System32` и вычищает все
  ключи IFEO;
- README честно пишет, что один файл кладётся в `System32`, и что это требование
  Application Verifier, а не наша прихоть.

**Почему это не нарушает смысл запрета.** Смысл был — «не ломать систему подменой
системных файлов». Мы не трогаем ни одного чужого файла, кладём рядом один свой с
именем, которого у Microsoft быть не может. Ровно так работает VxKex, на который проект
и опирается.

### Следствие для режима без прав администратора

Раз запись в `System32` требует прав администратора, **в режиме без них основной способ
недоступен целиком** — и никакой обходной записи в систему там быть не может. Для этого
режима остаётся принципиально другой путь: статическая перезапись таблицы импорта в
копии EXE плюс `fwd81_*.dll` рядом с программой.

Он **слабее**: не перехватывает динамическую загрузку через `LoadLibrary`/`GetProcAddress`.
Это записано честным долгом в [limitations.md](limitations.md), а не спрятано.

### Что сделано в коде и документах

- `docs/architecture.md`: раздел 5 переписан (VerifierDlls — основной способ с известной
  ценой в один файл), раздел 7 связан с режимом без админа, раздел 9 переписан целиком,
  открытый вопрос №1 помечен закрытым.
- `docs/limitations.md`: заведён; первая запись — слабость режима без админа.
- `README.md`: раздел «Один файл в System32 — и почему это не то, чего вы боитесь».
- `src/cli/main.c`: добавлена команда `uninstall` (пока честная заглушка, веха M2).

### Проверка сторожей на старую формулировку (пункт 3 задания)

Проверено: ни `tools/check_licenses.py`, ни `tools/check_image.py` не завязаны на правило
про System32 — поиском по `tools/` слов `System32`, `VerifierDlls`, `IFEO`, `подмен`,
`системн` совпадений ноль. Сторожа проверяют импорты, версию в заголовке и лицензии;
изменение правила их не касается, править нечего.

## 16.09.2026 — веха M1: анализатор (exportdiff + fwd81diag)

### Что сделано

- **`tools/exportdiff/exportdiff.py`** — сравнение экспортов System32 двух систем.
  Команды `export / diff / coverage / stubs / baseline / check`, всё одной командой
  `all`. Обход `C:\Windows\System32` (~3500 DLL, ~140 тыс. функций) занимает ~40 с.
- **`fwd81diag.exe`** — анализатор на чистом Win32: читает PE, достаёт требуемую
  версию Windows и импорт (обычный + отложенный), сверяет с базой и выдаёт вердикт.
- **`fwd81cli diag`** больше не заглушка: делегирует в `fwd81diag.exe` (одна
  реализация разбора, а не две).
- Документы: `tools/exportdiff/README.md`, обновлены `src/diag/README.md`, README,
  testing.md. `docs/coverage.md` и `src/diag/fwd81diag_baseline.h` — генерируемые.

### Принятые решения и причины

**1. Признак отсутствия данных 8.1 — явный, а не пустой список.**
`missing.json` при отсутствии копии System32 из 8.1 содержит `available: false` и
причину, а не пустой массив. Пустой массив означал бы «ничего не отсутствует» —
прямая ложь. То же в `fwd81diag`: без базы он честно говорит «вердикт невозможен»
(код 5), а не «всё хорошо». Это правило проекта №3 (признак отсутствия — вне
диапазона обычных значений) и №11 (не выдавать непроверенное за готовое).

**2. «Отсутствует» = нет имени НИГДЕ в 8.1, а не в конкретной DLL.**
Функции переезжают между библиотеками через apiset (kernel32 → kernelbase). Поэтому
членство проверяется в объединении всех экспортов 8.1, а результат группируется по
DLL из Windows 10. Иначе форварднутая функция ложно попала бы в «отсутствующие».
Проверено на синтетике: `SetThreadDescription` (нет нигде) → в missing;
`VirtualAlloc2` сгруппирован под kernelbase, а не kernel32 — верно.

**3. Единственный источник правды о покрытии — пометки в коде `src/libs`.**
`// FWD81-COVER: dll!func F/I/S/N since note`. `exportdiff` собирает их в
coverage.json и coverage.md. Пока src/libs пуст — покрытие честный ноль. Правило
«одна сущность — один путь»: не заводим отдельный список покрытия рядом с кодом.

**4. База для fwd81diag — генерируемый C-заголовок, а не чтение JSON в рантайме.**
`fwd81diag_baseline.h` встраивает имена функций 8.1 и покрытие прямо в exe. Так
анализатор — один переносимый файл без внешних зависимостей, что важно для запуска
на самой 8.1. Заголовок закоммичен в пустом виде; с настоящими данными
перегенерируется и коммитится заново.

**5. Что коммитим, что нет.** `exports-*.json`, `missing.json`, `coverage.json` и
заготовки `_generated_stubs` — производные от данных 8.1, которых в репозитории нет,
поэтому gitignored. В репозитории — только `docs/coverage.md` и
`fwd81diag_baseline.h`: их достаточно, чтобы собрать fwd81diag на CI.

**6. CI-проверка `check` проверяет только coverage.md.** Он выводится из src/libs —
данных, которые есть и на раннере. Файлы, зависящие от 8.1 (missing, baseline), на
CI не проверяются: там нет копии 8.1, и правильный ответ для них — «данных нет».
Проверять их против пустого состояния значило бы запретить коммитить настоящую базу.

### Гочи, найденные при реализации

- **`UnicodeEncodeError` на CI** (всплыл ещё в M0, но закреплён здесь): скрипты сами
  переключают stdout на UTF-8 — на раннере GitHub он по умолчанию cp1252.
- **`C1128: число секций превышает предел`**: с настоящей базой 8.1 во встроенный
  заголовок попадают десятки тысяч имён, и обычный объектный файл не вмещает. Лечится
  `/bigobj` у цели fwd81diag. На пустой базе флаг не мешает. Всплыло только на
  синтетике с реальными данными — на пустом состоянии сборка мгновенная.
- **Ложная тревога сторожа лицензий**: `exportdiff.py` (зона MIT) содержит строку
  `LGPL-2.1-or-later`, потому что ГЕНЕРИРУЕТ LGPL-заготовки. Добавлен точечный,
  названный поимённо, exempt — как у самого check_licenses.py. Проверка SPDX-шапки
  самого файла при этом осталась в силе.

### Что проверено своими руками

- Полная сборка Debug+Release со всеми сторожами — зелёная. `fwd81diag.exe`: одна
  зависимость KERNEL32, версия заголовка 6.3.
- exportdiff: обход System32, честное «данных 8.1 нет» во всех файлах, `check` зелёный.
- fwd81diag на notepad Win11 → версия 10.0 + предупреждение, код 5; на нашем
  fwd81cli.exe → версия 6.3.
- **Все три ветки вердикта — на живом входе** (синтетическая база без GetStdHandle):
  не покрыто → код 4, заглушка S → код 3, покрыто F → код 0.
- `fwd81cli diag` действительно делегирует в fwd81diag.exe и возвращает его код.

### Что НЕ проверено

- **Ничего не сверено с настоящей Windows 8.1** — базы нет, вердикт по функциям на
  реальных данных не проверялся. Сценарий сверки готов в testing.md.
- Отложенный импорт (delay-load) реализован по современному RVA-формату; на файле с
  настоящим delay-load вживую не гонялся — не нашлось под рукой подходящего.
- Форвардеры и импорт по ординалу анализатор пока не разбирает (ординалы пропускает
  осознанно: по имени их с базой не сверить).

### Открытые вопросы (в дополнение к прежним)

5. **Размер и скорость базы fwd81diag.** Настоящая 8.1 даст ~60–80 тыс. имён; сейчас
   они встроены как отдельные строковые литералы. Собирается за секунды с `/bigobj`,
   но если станет тяжело — перейти на один общий блоб с индексом. Пока не трогаю.

### Что дальше

Веха **M2**: `fwd81core.dll` без CRT, внедрение через реестр IFEO, лог факта загрузки.
Первый шаг M2 требует живой 8.1 (проверить, что VerifierDlls реально подхватывает наш

## 16.09.2026 (вечер) — веха M2: ядро без CRT + журнал + команды IFEO

### Что сделано

- **Журнал ядра** (`src/core/fwd81log.c`) — запись событий из `fwd81core.dll` без
  библиотеки языка C, только через нативные функции `ntdll` (`NtCreateFile`,
  `NtWriteFile`, `RtlQueryEnvironmentVariable_U`, `RtlUnicodeToUTF8N`,
  `NtQuerySystemTime`, `RtlTimeToTimeFields`, `NtQueryInformationProcess`). Пишет
  в `%LOCALAPPDATA%\Fwd81\logs\fwd81.log`: время, PID, событие, путь к образу.
- **Ядро на загрузке** пишет «загружено в процесс», на выгрузке — «выгружено».
  В точке входа — только запись в журнал (нативные вызовы, без LoadLibrary и
  ожиданий): правило про loader lock соблюдено.
- **`src/core/fwd81_mem.c`** — свои `memset`/`memcpy`: оптимизатор MSVC сам
  сворачивает циклы заполнения/копирования в вызовы этих функций, а CRT у ядра нет.
- **Команды `fwd81cli`**: `enable` (скопировать ядро в System32 + прописать IFEO:
  GlobalFlag=0x100, VerifierDlls=fwd81core.dll), `disable` (снять наши значения,
  чужие настройки отладчика не трогать), `uninstall` (снять во всех программах +
  убрать файл из System32), `log` (показать журнал). Модуль `src/cli/ifeo.c`,
  вывод вынесен в общий `src/cli/out.c`.
- **`--dry-run`** у enable/disable/uninstall: печатает план, ничего не меняя.

### Принятые решения и причины

**1. Журнал в ядре — только нативные `Nt*`/`Rtl*`, не kernel32.**
Ядро грузится раньше CRT и обязано зависеть только от ntdll (проверяет
`check_image.py`). Поэтому и файл, и время, и данные о процессе берутся через
ntdll. `OutputDebugString` в ядре пока не используется — она в kernel32; добавим
через нативный механизм отладочной печати позже, если понадобится.

**2. Свои memset/memcpy с `#pragma function`.** Без прагмы тело memset,
написанное циклом, компилятор свернул бы в вызов самого себя (бесконечная
рекурсия). Прагма заставляет считать их настоящими функциями.

**3. Границу разбирали эмпирически: что можно проверить без живой системы.**
Полное внедрение через IFEO требует записи в System32 и HKLM (права
администратора) — это правка живой системы, её без явного слова Арсения не
делаю. Но journalирование ЯДРА проверяется иначе: тестовый процесс грузит ядро
через `LoadLibrary` (срабатывает `DLL_PROCESS_ATTACH`) — это не трогает ни
System32, ни реестр. Так механизм журнала проверен по-настоящему, отдельно от
механизма внедрения.

**4. `enable` пишет GlobalFlag как REG_DWORD 0x100.** Это флаг
FLG_APPLICATION_VERIFIER; так его пишет и штатный gflags. VerifierDlls — REG_SZ
с одним именем файла (без пути): полные пути механизм не принимает, отсюда и
копирование в System32.

**5. `disable`/`uninstall` не удаляют чужое.** Снимаем только свои два значения;
ключ программы удаляем целиком лишь если после этого он пуст. `uninstall`
находит «свои» программы по метке VerifierDlls==fwd81core.dll.

### Что проверено своими руками

- Полная сборка Debug+Release, все сторожа зелёные. Ядро — зависимость только
  `ntdll` (была 0, стала 1: появилась логика). cli — ADVAPI32+KERNEL32, версия 6.3.
- **Журнал вживую**: ядро загружено в процесс powershell через LoadLibrary →
  в `fwd81.log` появились строки загрузки и выгрузки с временем, PID, кириллицей
  (UTF-8) и путём к образу. `fwd81cli log` их показывает.
- `enable --dry-run notepad.exe` — верный план (System32 + ключ IFEO), без записи.
- `uninstall --dry-run` — перечисление IFEO только на чтение, ничего не тронуто.
- CI получил шаг «ядро загружается и пишет журнал» (LoadLibrary + проверка файла).

### Что НЕ проверено (и почему это честно важно) — на момент написания кода

- **Само внедрение через IFEO вживую не проверено.** Не запускал `enable` без
  `--dry-run`: это записало бы файл в System32 и ключи в HKLM живой машины. Нужно
  либо явное слово Арсения на такую проверку здесь (Win11 тоже поддерживает
  VerifierDlls), либо виртуальная машина с 8.1. До этого «внедрение работает»
  не утверждаю (правило №1: механизм не равен кнопке; №11: не объявлять готовым
  непроверенное).
- `OutputDebugString`-канал журнала в ядре пока не сделан (нужен нативный путь).

> **ОБНОВЛЕНО 16.09.2026 — внедрение через IFEO ПРОВЕРЕНО вживую (см. запись ниже).**
> `OutputDebugString`-канал по-прежнему не сделан.

### Подготовка к живой проверке внедрения (по требованиям Арсения)

Перед первым живым запуском `enable` Арсений выставил четыре условия — все
выполнены до запуска:

1. **Чёрный список в `enable`.** Жёсткий отказ (код 7, без обхода флагом) для
   winlogon/csrss/lsass/services/smss/wininit/explorer/svchost/dwm/taskhostw.
   Проверено: `enable --dry-run svchost.exe` → отказ. Причина: сбой ядра в таком
   процессе = незагружаемая система.
2. **Числовая причина вызова точки входа в журнале.** Теперь пишется
   `reason=<n>`. Критерий успеха M2: в журнале есть `reason=4`
   (DLL_PROCESS_VERIFIER) РАНЬШЕ `reason=1` (DLL_PROCESS_ATTACH). Проверено, что
   через LoadLibrary приходит только `reason=1` (и `reason=0` на detach), а
   `reason=4` нет: значит эта запись доказывает именно внедрение, а не загрузку.
3. **Регистрация провайдера Application Verifier.** На `DLL_PROCESS_VERIFIER` ядро
   возвращает описатель `RTL_VERIFIER_PROVIDER_DESCRIPTOR` (структуры объявлены
   сами — в обычном SDK их нет) и пишет в журнал результат. Без этого часть
   процессов не стартует.
4. **`docs/otkat.md`** — точные команды ручного отката (reg delete + del) из cmd
   от администратора, на случай если `uninstall` не сработает.

Живой запуск по порядку: точка восстановления → `enable --dry-run` (жду «да»
Арсения) → `enable` + запуск пробника + журнал целиком → сразу `disable` +
`uninstall` + проверка чистоты System32 и реестра. Defender не обходить.

- Закрыть проверку внедрения: с разрешения Арсения прогнать `enable` на
  безобидном пробнике здесь (и `uninstall` следом), либо дождаться ВМ с 8.1.
- Веха **M3**: перехваты загрузчика (`LdrLoadDll`, `LdrGetProcedureAddress*`,
  apiset), подстановка отсутствующих функций, контрольный пример `tests/synthetic`.

## 16.09.2026 (позже) — живая проверка внедрения через IFEO: успех

Арсений запустил VS Code от администратора и дал провести проверку по строгому
порядку. Точку восстановления пропустили — свежая уже была. Между шагами вывод
показывался целиком, я ничего не склеивал.

### Что сделали (на безобидном пробнике fwd81probe.exe — копия fwd81cli.exe)

1. `enable --dry-run fwd81probe.exe` — показан план, без записи.
2. По явному «да» Арсения — `enable fwd81probe.exe`: файл скопирован в System32,
   ключ IFEO создан. Код 0. Defender/Kaspersky не помешали.
3. Запуск `fwd81probe.exe version` — процесс стартовал нормально (код 0), то есть
   регистрация провайдера НЕ сломала старт.
4. `fwd81cli log` — журнал для `image=...fwd81probe.exe` (pid=21308):
   ```
   reason=4  (DLL_PROCESS_VERIFIER)
   провайдер Application Verifier зарегистрирован (ok)
   reason=1  (DLL_PROCESS_ATTACH)
   reason=0  (DLL_PROCESS_DETACH)
   ```
5. Сразу `disable fwd81probe.exe` + `uninstall`.
6. Проверка чистоты: ключа IFEO нет, `System32\fwd81core.dll` нет, ключей с
   `VerifierDlls=fwd81core.dll` в IFEO не осталось нигде.

### Что это доказывает

**`reason=4` пришёл РАНЬШЕ `reason=1`** — это и есть критерий успеха M2. Через
обычный `LoadLibrary` бывает только `reason=1` (первые строки того же журнала, от
раннего теста в powershell — там нет `reason=4`). Значит механизм `VerifierDlls`
реально подхватил наш `fwd81core.dll` из System32 и внедрил ядро в целевой процесс
через Application Verifier. Провайдер зарегистрировался — процесс не сломался.

**Открытый вопрос №1 закрыт опытом, а не рассуждением:** библиотека-поставщик,
лежащая в System32, действительно подхватывается механизмом VerifierDlls.
`uninstall` убирает всё начисто — откат работает.

Не проверено по-прежнему: поведение на НАСТОЯЩЕЙ Windows 8.1 (проверка была на
Win11; механизм тот же, но целевая ОС другая) — закроется на ВМ, когда появится.

### Итог: веха M2 закрыта полностью

Ядро без CRT, журнал загрузки, внедрение через IFEO — всё есть и проверено вживую.

## 16.09.2026 — M3, пункт 1: контрольный пример tests/synthetic

Начал M3 (перехваты загрузчика). План согласован с Арсением, порядок не меняю.
Две поправки от него: (1) `run` — только инструмент разработки, закрытие M3
засчитывается ТОЛЬКО по боевому пути IFEO; (2) слой перехвата выбрать сразу на
IFEO (пункт 3). Плюс требование: synthetic должен ломаться тем же путём, каким
реальные программы дёргают загрузчик (статический импорт), а не искусственным
LoadLibrary — иначе перехват «удобного» вызова засчитан не будет.

### Что сделано

`tests/synthetic/` — две программы, падающие при ЗАГРУЗКЕ через статическую
таблицу импорта (не рантайм-вызов):
- `synthetic_absent_dll` — импорт из несуществующей `fwd81_absent.dll` (отказ №2);
- `synthetic_absent_proc` — импорт несуществующей функции из настоящей kernel32
  (отказ №3).

Хитрость: импорт из несуществующего нельзя слинковать напрямую, поэтому из `.def`
через `lib.exe` генерируется импорт-библиотека — она удовлетворяет символ на
линковке, а провал происходит при загрузке, как у настоящей программы.

### Измеренная база (без Fwd81)

Прогон с погашенными диалогами загрузчика (`SetErrorMode 0x8003`) и таймаутом:
- `synthetic_absent_dll`  → exit `0xC0000135` (STATUS_DLL_NOT_FOUND), main не достигнут;
- `synthetic_absent_proc` → exit `0xC0000139` (STATUS_ENTRYPOINT_NOT_FOUND), main не достигнут.
Маркер `SYNTHETIC-REACHED-MAIN` не печатается. Конструкция подтверждена и `fwd81diag`:
он видит в импорте `fwd81_absent.dll` и `Fwd81AbsentProcedure`.

Критерий успеха M3: под IFEO ядро перехватывает разрешение, подставляет заглушку,
процесс доходит до main (печатает маркер), в журнале — запись о перехвате. `run`
даёт тот же прогон без админа для разработки, но зачёт — только по IFEO.

### Админские шаги M3 (копим на один заход)

Пока НЕТ ни одного — пункт 1 прав администратора не требовал. Список пополнится к
финальной боевой проверке перехвата под IFEO (enable пробника + запуск + журнал +
disable/uninstall), тогда попрошу права одним заходом.

## 16.09.2026 — M3, пункт 2: fwd81cli run + delay-synthetic

По решению Арсения (вариант 1): `run` строю как дев-инструмент с жёстко
очерченным потолком, зачёт M3 — только по IFEO.

### Что сделано

- **`fwd81cli run <exe> [args]`** (`src/cli/run.c`) — запуск программы с внедрением
  ядра БЕЗ реестра и System32: CreateProcess(SUSPENDED) → запись пути ядра в память
  процесса → CreateRemoteThread(LoadLibraryW) → ждём загрузки → ResumeThread. Гасит
  модальные окна загрузчика (SetErrorMode), ждёт завершения с таймаутом, возвращает
  код программы. При неудаче внедрения снимает свой же приостановленный процесс.
- **Потолок зафиксирован** в run.h, в справке cli и таблицей в `architecture.md`:
  run чинит delay-load и рантайм LoadLibrary, но НЕ статические импорты EXE.
- **Третий контрольный пример** `synthetic_delay_absent` — та же несуществующая DLL,
  но подключена как `/DELAYLOAD`. Загрузка откладывается до первого вызова, поэтому
  процесс доходит до main (в отличие от статического synthetic).

### Таблица «способ загрузки → путь починки» (в architecture.md)

| Способ | Когда разрешается | IFEO | run |
|---|---|:--:|:--:|
| статический импорт | до первой инструкции (LdrpInitializeProcess) | да | нет |
| delay-load | при первом вызове функции | да | да |
| LoadLibrary/GetProcAddress | когда программа сама вызовет | да | да |

### Проверено (без админа)

`fwd81cli run synthetic_delay_absent.exe`:
- журнал получил `reason=1 image=…synthetic_delay_absent.exe` — ядро внедрилось
  именно в целевой процесс (а не в fwd81cli);
- программа дошла до main (`REACHED-MAIN delay before-call`);
- delay-вызов пока провалился: `0xC06D007E` (ERROR_MOD_NOT_FOUND) — перехватов ещё
  нет. Это измеренная база delay-пути: в пункте 3 здесь должно стать `DELAY-CALL-OK`.
