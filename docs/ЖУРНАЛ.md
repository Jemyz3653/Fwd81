## 15.09.2026 — веха M0: каркас

### Что сделано

- Заведён репозиторий в `C:\Fwd81` поверх существующей истории GitHub (первый
  коммит от 14.09.2026 сохранён, не затёрт).
- Собран каркас: система сборки на CMake + Ninja, два скрипта запуска, CI на GitHub
  Actions, документация, два сторожа-проверки.
- Собирается и работает: `fwd81core.dll` (пустой каркас ядра, без библиотеки языка C)
  и `fwd81cli.exe` (команды `version` и `help`; остальные честно отвечают, что ещё
  не реализованы).

### Принятые решения и причины

**1. Две лицензии вместо одной, граница по каталогам.**
В репозитории лежала MIT (создана вместе с репозиторием на GitHub), в задании
значилась LGPL-2.1+. Решение владельца проекта: ядро, библиотеки реализаций и
заглушки apiset — под LGPL-2.1-or-later, утилиты и инструменты — под MIT.

Причина: LGPL в зоне ядра нужна, чтобы иметь право брать код Wine. Утилиты
заимствований не содержат, им ограничения ни к чему.

Отдельно уточнено (и это важная поправка к заданию): **ReactOS лицензирован под
GPL-2.0-or-later, а не под LGPL.** Произвольный файл оттуда утянул бы весь проект
в GPL. Легальный источник заимствований остаётся один — Wine, плюс те файлы
ReactOS, где в шапке явно указан LGPL и происхождение из Wine. Подробности —
в [licensing.md](licensing.md).

**2. Генератор сборки — Ninja Multi-Config, а не генератор Visual Studio.**
На этой машине CMake 4 с генератором Visual Studio в некоторых проектах падает на
`ucrtd.lib`. Ninja этой проблемы не имеет и собирает быстрее. Обе конфигурации
(Debug и Release) настраиваются одним заходом.

**3. `build.ps1` сам поднимает окружение компилятора.**
Отдельная «командная строка разработчика» не нужна: скрипт находит Visual Studio
через `vswhere` (обязательно с ключом `-products *`, иначе не видно Build Tools)
и импортирует окружение `vcvars64.bat`.

Попутно вылезла особенность этой машины: в ней включён
`NoDefaultCurrentDirectoryInExePath`, из-за чего `vcvars64.bat` не находит свой же
`vswhere.exe` и пишет `is not recognized`. Окружение при этом всё равно
поднималось, но шум в выводе убран — каталог установщика добавляется в PATH
перед вызовом.

**4. Утилиты собираются со статической библиотекой языка C.**
Требование задания — утилиты должны запускаться на самой Windows 8.1. Статическая
CRT снимает зависимость и от `vcruntime140.dll`, и от обновления UCRT KB2999226,
которого на машине пользователя может не быть. Результат: `fwd81cli.exe` зависит
ровно от одной библиотеки — `KERNEL32.dll`. Проверено на собранном файле.

**5. Метка подсистемы 6.03 у всех наших исполняемых файлов.**
Иначе компоновщик пишет в заголовок «нужна Windows 10.0», и 8.1 откажется
запускать файл ещё до поиска функций — то есть мы наступили бы ровно на ту
проблему, которую чиним. Задаётся флагом `/SUBSYSTEM:<вид>,6.03`.

**6. Три правила проекта отданы сторожам, а не дисциплине.**
Правило, которое проверяет человек, забывается на третьей неделе.

| Сторож | Что ловит |
|---|---|
| `tools/check_image.py` | зависимость ядра от чего-либо кроме `ntdll.dll`; требование Windows выше 6.3 в заголовке |
| `tools/check_licenses.py` | нарушение лицензионной границы между каталогами |

**7. Сторожа проверены поломкой, а не рассуждением.** Каждому подсовывали заведомо
испорченный вход, и каждый обязан был упасть **и назвать имя виновника**:

- проверка зависимостей: натравлена на `fwd81cli.exe` с правилом «только ntdll» →
  назвала `KERNEL32.dll`, код возврата 1;
- проверка версии в заголовке: натравлена на `C:\Windows\System32\notepad.exe` →
  «требование Windows 10.0», код возврата 1;
- проверка лицензий, три случая: MIT-файл в каталоге `src/core`; файл без пометки
  SPDX вовсе; файл в каталоге, не описанном в правилах. Все три отвергнуты с именем
  файла.

**8. Каталоги будущих частей не пустые, а с объяснением.**
В `src/libs`, `src/apisets`, `src/diag`, `src/cfg` лежит `README.md`: что там
появится и в какой вехе. Пустой каталог без объяснения — это вопрос «а это вообще
живое?» через два месяца.

**9. Незаконченное говорит о себе вслух.**
`fwd81cli` на команды `diag`, `enable`, `run`, `patch`, `list`, `log` отвечает
текстом «появится в вехе такой-то» и кодом возврата 2. Ни одна команда не делает
вид, что отработала. Заглушка, которая молча врёт «всё получилось», в проекте
запрещена.

### Что проверено своими руками

- Сборка с нуля в Debug и Release — проходит.
- `fwd81cli.exe version` и `help` — выводят русский текст без «кракозябр».
- `fwd81cli.exe diag test.exe` — код возврата 2, честное сообщение.
- `fwd81core.dll` — в таблице импорта **ноль** зависимостей (кода, который звал бы
  ntdll, там пока просто нет), требование в заголовке 6.0.
- `fwd81cli.exe` — одна зависимость `KERNEL32.dll`, требование в заголовке 6.3.
- Все три сторожа — падают там, где должны.

### Что НЕ проверено

- **Ничего не проверено на живой Windows 8.1.** Виртуальной машины пока нет.
- CI на GitHub Actions написан, но ни разу не запускался: изменения ещё не
  отправлены на GitHub.

### Открытые вопросы

1. **Где должен лежать `fwd81core.dll`, чтобы механизм `VerifierDlls` его нашёл.**
   У Application Verifier есть известное ограничение: библиотеку-поставщика система
   может искать в `%SystemRoot%\System32`, а класть туда что-либо нам запрещено
   жёстко. Запасные пути описаны в [architecture.md](architecture.md), раздел 5.
   **Закрыть опытом на виртуальной машине до начала вехи M2.** Это самый крупный
   риск проекта: если способ внедрения не подтвердится, меняется вся веха M2.

2. **Работает ли статическая CRT из Visual Studio 2022 на живой 8.1.**
   Сценарий проверки готов и лежит в [testing.md](testing.md) — выполнить сразу,
   как появится виртуальная машина.

3. **Класть ли в репозиторий выгрузки `exportdiff`** (`data/exports-*.json`).
   Пока отключены в `.gitignore`. Решение — в вехе M1, когда станет виден их размер.

4. **Лицензия каталога `tests/`** назначена MIT по умолчанию, владельцем проекта не
   подтверждена. Тестов пока нет; вернуться в вехе M3.
